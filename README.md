# Jumia Sentiment Analysis

A machine learning system that classifies Jumia Nigeria product reviews as
**Positive** or **Negative**, served through a FastAPI web application with
a live classifier and an evaluation dashboard.

## Project Objectives

1. **Design** a sentiment analysis system for Jumia Nigeria customer reviews
   — see *System Architecture* below.
2. **Implement** the system using machine learning techniques — Naive Bayes
   and Logistic Regression, trained on real Jumia review data.
3. **Evaluate** performance using multiple metrics — precision, recall, F1,
   accuracy, ROC-AUC, and 5-fold cross-validation, all viewable on the
   `/dashboard` page.

## Features

- **Single review classifier** (`/`) — paste one review, get an instant
  sentiment prediction with confidence.
- **Batch upload** (`/upload`) — upload a CSV of many reviews (up to 5,000
  rows / 5MB) and get a full sentiment breakdown, a preview table, and a
  downloadable results CSV.
- **Evaluation dashboard** (`/dashboard`) — model comparison metrics, charts,
  and a lightweight upload history (no login required).

## System Architecture

```
Raw Reviews (CSV)
      │
      ▼
Preprocessing  (clean text, label sentiment from star rating)
      │
      ▼
Feature Extraction  (CountVectorizer — Bag of Words)
      │
      ▼
Model Training  (Naive Bayes, Logistic Regression)
      │
      ▼
Saved Artifacts  (models/*.pkl, models/metrics.json, charts/*.png)
      │
      ▼
FastAPI Application
   ├── "/"           → live review classifier (form + JS + /api/predict)
   ├── "/upload"      → batch CSV classifier (/api/batch-predict)
   └── "/dashboard"  → model comparison table, charts, and upload history
```

Training happens **offline** (`train_model.py`) rather than on every web
request — this is standard ML-system practice: train once, save the model,
load the saved model at server startup for fast predictions.

## Setup

### 1. Create a virtual environment (recommended)

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
```

### 2. Install dependencies

```bash
pip install -r requirements.txt
```

### 3. Train the models

This reads `data/jumia_reviews_df_multi_page.csv`, trains both models,
and generates everything in `models/` and `app/static/charts/`.

```bash
python train_model.py
```

You only need to re-run this if the dataset changes — the web app loads
the saved `.pkl` files, it doesn't retrain on every request.

### 4. Run the web application

```bash
uvicorn app.main:app --reload
```

Then open **http://127.0.0.1:8000** in your browser.

- `/` — paste a review, pick a model, see the predicted sentiment and the
  model's confidence
- `/dashboard` — dataset stats, model comparison table (precision, recall,
  F1, accuracy, ROC-AUC, cross-validation), and all charts

## Design Decisions Worth Knowing for a Defense

- **Labeling rule**: ratings of 3★ and above are labeled Positive, below 3★
  Negative. This is a judgment call — a stricter rule (e.g. only 4-5★ as
  Positive) is a reasonable alternative and worth discussing.
- **Class imbalance**: the dataset is heavily skewed — 1,957 positive vs.
  60 negative reviews. `class_weight="balanced"` is used for Logistic
  Regression to compensate; Naive Bayes doesn't support this directly,
  which is part of why its recall on the minority class is weaker. This is
  intentionally left visible in the metrics rather than hidden, because
  it's a legitimate limitation to discuss in a defense.
- **Stratified train/test split**: ensures the small negative class is
  proportionally represented in both the training and test sets, rather
  than a random split that could leave the test set with almost no
  negative examples.
- **5-fold cross-validation**: reported alongside the single train/test
  split metrics, since one split can be misleading with so few negative
  examples.
- **Why Naive Bayes vs. Logistic Regression**: Naive Bayes is a fast,
  simple probabilistic baseline commonly used for text classification;
  Logistic Regression is a stronger linear baseline that generally
  performs better on text and gives interpretable feature weights.

## Batch Upload — Design Decisions Worth Knowing for a Defense

- **Why a row/size cap (5,000 rows / 5MB)?** The batch endpoint processes
  synchronously (within a single request) rather than as a background job.
  A generous but bounded limit keeps every request fast and predictable,
  which avoids the complexity of a job queue while still supporting a
  genuinely large batch. This is a deliberate scope decision — a
  production system handling unbounded uploads would move to background
  processing (e.g. a task queue), which is noted under Future Work.
- **Why a fixed required column name (`review_text`) instead of letting
  the user map columns?** It keeps the upload flow simple and predictable.
  The tradeoff is documented, not hidden — the upload page states the
  requirement clearly, and a missing column produces a clear error message
  rather than a crash or a silent wrong result.
- **Why no accuracy metrics on uploaded batches?** Precision, recall, F1,
  and ROC-AUC all require a known true label to compare predictions
  against. Uploaded reviews have no such label — the model is predicting
  their sentiment, not being tested against a known answer. The dashboard
  is deliberately explicit about this distinction: the model comparison
  table (precision/recall/F1/accuracy/AUC) only appears for the labeled
  training/test data; the Upload History section only shows what the
  model predicted, not how accurate it was.
- **Why no authentication/user accounts?** Auth was considered and
  deliberately deferred — see Future Work. Upload history is a shared,
  session-less log by design, appropriate for a demo/defense context
  rather than a multi-user production deployment.

## Possible Extensions (Future Work)

- Add a third model (e.g. SVM) for a richer comparison
- Live-scrape fresh reviews from Jumia Nigeria instead of using a static CSV
- Add user accounts/authentication to support personalized, private upload
  history and to protect the API in a real deployment
- Move batch processing to a background job queue to support uploads
  larger than the current 5,000-row/5MB limit without risking request timeouts
- Add SMOTE or other oversampling techniques to address class imbalance
- Show word-level feature importance for individual predictions (explainability)
- Let users map their own CSV's column name instead of requiring `review_text`
